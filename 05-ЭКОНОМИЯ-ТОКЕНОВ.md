# 05 · Экономия токенов: что реально нужно, а что нет

Вы спросили конкретно про Obsidian, Ollama «и что-то в этом роде». Отвечаю по
существу, с проверкой, и без ритуального «поставьте всё на всякий случай».

**Дата проверки: 14 августа 2026.**

---

## Короткий ответ

- **Obsidian — не нужен.** Ваш проект уже устроен как файловая память
  (`brief/`, `sites/`, `CLAUDE.md`). Это то же самое, что даёт Obsidian+MCP,
  только без лишнего слоя.
- **Ollama — не нужен для дизайна и текстов.** Локальные модели годятся для
  объёмной, повторяющейся, нетребовательной к вкусу работы. У вас — наоборот:
  штучные B2B-сайты, где решает вкус арт-директора и точность текста.
- Реальная экономия в вашем случае — это **три бесплатных настройки**, я их
  внёс в проект: маршрутизация моделей по агентам, дисциплина `/clear` и
  `/compact`, и один плагин для видимости расхода. Ниже — почему именно так.

---

## 1. Обсидиан. Разбор, а не отказ с порога

### Что это вообще такое в связке с Claude

Obsidian — приложение для заметок на локальных Markdown-файлах. Через MCP
Claude Code может читать и писать в такое хранилище напрямую <cite index="36-1">using the MCP protocol, with Claude reading and writing markdown notes organized by project</cite>.
Есть минимум три способа подключения: `mcp-obsidian` (нужен запущенный
Obsidian и его плагин Local REST API), `obsidian-mcp-plugin` (работает как
граф знаний с переходами по ссылкам), и просто **Filesystem MCP**, потому что
хранилище Obsidian — это обычная папка с `.md`-файлами <cite index="41-1">and MCP servers can connect Claude to an Obsidian vault via the Local REST API, direct filesystem access, or a native plugin that exposes the vault as an MCP server</cite>.

Смысл для разработчика: не начинать каждую сессию с нуля, объясняя заново
контекст проекта <cite index="40-1">every conversation with Claude starts from zero, and without persistent memory the same context has to be retyped each session</cite>.

### Почему это не ваш случай

Вся идея Obsidian-интеграции — компенсировать то, чего у Claude Code нет по
умолчанию: **связную папку с накопленным контекстом между сессиями.**

У вас это уже есть, устроено проще и без лишней зависимости:

| Что даёт Obsidian+MCP | Что у вас уже есть |
|---|---|
| Markdown-заметки по проектам | `brief/<slug>.md` — один файл на заказ |
| Долговременная память решений | `CLAUDE.md` — правила проекта, читаются автоматически |
| Поиск по накопленным заметкам | `sites/<slug>/content.md`, `tokens.css` — уже структурировано по папкам |
| Граф связей между темами | Вам не нужен: сайты клиентов друг с другом не связаны |

Добавление Obsidian означает: держать приложение запущенным (для варианта с
Local REST API — обязательно, иначе MCP не работает) <cite index="42-1">the mcp-obsidian server requires the Local REST API community plugin installed in Obsidian, which means Obsidian must be running for the MCP to work</cite>,
плюс лишний процесс, плюс синхронизацию двух источников правды — файлов
проекта и заметок в хранилище. Это чистые издержки без выгоды именно для
фабрики сайтов, где каждый заказ и так изолирован в своей папке.

**Когда Obsidian имел бы смысл:** если бы вы вели через Claude десятки разных
проектов одновременно и хотели единый поиск по всем решениям сразу — «как я
в марте решал похожую задачу с другим клиентом». Для одной студии сайтов —
избыточно.

### Лёгкая альтернатива, если всё же хочется постоянную память

Если через полгода вы захотите, чтобы Claude сам запоминал паттерны между
заказами («этому клиенту не нравятся закруглённые углы») — есть более лёгкий
вариант, чем Obsidian: **Basic Memory MCP** <cite index="40-1">Basic Memory is an open-source MCP server that gives Claude a persistent, local knowledge base, stored entirely as plain Markdown files with a local SQLite index for fast search</cite>.
Никакого отдельного приложения — просто папка с файлами и SQLite-индексом,
который можно удалить и пересобрать из markdown в любой момент.
Репозиторий существует и доступен (проверено, HTTP 200).

Пока не нужно — не ставьте. Добавите, когда почувствуете конкретную боль
«опять объясняю то же самое».

## 2. Ollama. Разбор с той же строгостью

### Что это технически даёт

Ollama — раннер для локальных моделей (Llama, Qwen, gpt-oss и другие) на
вашей машине. С января 2026 у Ollama есть совместимость с Anthropic Messages
API <cite index="51-1">Ollama added support for the Anthropic Messages API in January 2026, enabling Claude Code to connect directly to any Ollama model</cite>,
то есть Claude Code можно направить не на серверы Anthropic, а на локальную
модель — полностью бесплатно и офлайн.

Более тонкий сценарий — не замена Claude, а **делегирование части задач**:
Claude остаётся оркестратором в облаке, а рутинные куски (написание
шаблонного кода, ревью, объяснение файла) уходят на локальную модель через
MCP-мост. Есть минимум два готовых инструмента под это: `claude-sidekick`
<cite index="45-1">an MCP server that connects Claude to local Ollama models, allowing you to offload simpler tasks and save Claude tokens for complex work</cite>
и набор субагентов `claude-ollama-agents` <cite index="46-1">Claude Code subagents that delegate code generation, review, and testing to local Ollama models — Claude plans and reviews, Ollama writes</cite>.
Оба репозитория существуют (проверено).

### Почему для вашего проекта это плохая идея

Три причины, конкретно под вашу задачу:

**1. Профиль задач не совпадает.** Локальное делегирование окупается на
объёмной, повторяющейся, невзыскательной к качеству работе — массовые правки,
рутинные тесты, извлечение ключей i18n. Ваш пайплайн — обратный: три сайта в
месяц, где решает **вкус** (арт-директор выбирает направление) и **точность**
(копирайтер не имеет права придумать сертификат). Локальные модели пока
заметно слабее именно в этом — эстетическом суждении и надёжном следовании
узким инструкциям.

**2. Нет штатной маршрутизации по агентам.** По состоянию на март 2026 в
самом Claude Code открыт запрос на функцию «разные субагенты — разным
провайдерам» — она ещё не реализована <cite index="47-1">there's no way to route individual subagents to different providers within the same session; the model parameter in agent definitions only accepts sonnet, opus, haiku, all pointing to the same provider endpoint</cite>.
Значит, «оркестратор — Claude, а часть субагентов — на Ollama» из коробки не
работает. Придётся городить внешний MCP-мост поверх и так работающего
проекта — рост сложности ради задачи, которой у вас нет.

**3. Требования к железу.** Модель, которую рекомендуют для приличного
кода — Qwen3-Coder 30B — заточена под GPU c 24GB VRAM <cite index="50-1">Qwen3-Coder 30B A3B is the best 24GB choice for local coding, with gpt-oss 20B and Qwen2.5-Coder 14B/7B as smaller-card fallbacks</cite>.
Это не рабочая станция для 1С и офисных задач — это отдельная видеокарта
уровня RTX 4090, купленная только ради экономии на токенах для сайтов,
которые вы делаете нечасто.

**Вывод:** Ollama решает проблему «я плачу за токены на рутинный код в
промышленном темпе разработки». У вас проблема другая: «я хочу, чтобы шесть
согласованных агентов не жгли контекст впустую на одном заказе». Это чинится
не сменой модели, а дисциплиной внутри Claude Code — см. раздел 3.

## 3. Что реально экономит токены в вашем проекте — уже внесено

Вот что я поменял в файлах и почему, с опорой на официальную документацию
Claude Code и практику из проверенных источников.

### 3.1. Маршрутизация моделей по агентам — сделано

Было: `frontend-builder` и `motion-engineer` на Opus. Стало: **Sonnet**.

Почему: Opus нужен там, где решает суждение без права на ошибку —
направление дизайна (`art-director`) и B2B-тексты, где выдумка стоит
репутации (`copywriter`, оставлен на Opus). Вёрстка и анимация — это
реализация уже принятого решения по готовым токенам и текстам, здесь Sonnet
достаточно, а по официальной документации именно выбор модели — один из
рычагов управления стоимостью, наравне с контекстным менеджментом <cite index="31-1">Claude Code tracks token usage and reduces costs through context management, model selection, extended thinking settings, and preprocessing hooks</cite>.

Проверьте актуальные цены моделей на <https://claude.com/pricing> перед
масштабной работой — цифры вроде «Sonnet дешевле в несколько раз» я нашёл в
непроверенных источниках и **не привожу как факт**, только направление.

### 3.2. Дисциплина `/clear` и `/compact`

Не файл, а привычка — добавил в `CLAUDE.md`. Официальная логика простая:
контекст — самый дорогой ресурс, потому что вы платите за весь накопленный
диалог на каждом следующем шаге <cite index="29-1">context is the most expensive resource in Claude Code — every message accumulates in the context window, and you pay for all of it on every subsequent turn</cite>.

Практическое правило, которое стоит внести в привычку:

- **`/clear` между заказами.** Закончили сайт для клиента А — не тащите его
  контекст в работу над клиентом Б внутри той же сессии.
- **`/compact` внутри одного заказа**, когда чувствуете, что сессия
  разрослась — лучше на 60% заполнения контекста, чем ждать автоматического
  сжатия на 90%, потому что чем раньше сжатие, тем меньше теряется важного <cite index="35-1">a reasonable trigger threshold for /compact is around 60% context utilization, not 90%, because the earlier it happens, the better the summary retains what matters</cite>.
- Можно с подсказкой: `/compact сохрани только выбранное направление и итоговые токены дизайна`.

### 3.3. MCP только нужный

У вас в `.mcp.json` только `playwright` — это правильно. Каждый
дополнительный MCP-сервер добавляет описание своих инструментов в каждый
запрос <cite index="29-1">disable unused MCP servers, because each MCP server adds its tool schemas to every turn</cite>.
Не подключайте Figma MCP «про запас» — добавляйте только когда реально
пришёл заказ с готовым макетом.

### 3.4. Видимость расхода — один плагин, по желанию

Если хотите видеть в реальном времени, сколько сжигается на сессию,
существует бесплатный плагин `claude-hud` — статус-строка в терминале с
контекстом, активными инструментами и лимитами <cite index="55-1">Claude HUD uses Claude Code's native statusline API to render live session telemetry — context window fill, tool activity, subagent status — directly below the input, with no separate window or tmux required</cite>.
Репозиторий существует (проверено). Не обязателен, но полезен именно чтобы
поймать разрастание контекста до того, как оно ударит по кошельку:

```
/plugin marketplace add jarrodwatts/claude-hud
/plugin install claude-hud
```

### 3.5. Про «сжатый» стиль ответов (caveman) — сознательно не включаю

Существует целый класс скиллов, заставляющих Claude отвечать телеграфно ради
экономии выходных токенов. Репозиториев несколько (`JuliusBrussee/caveman`,
`carlosduplar/caveman-output-style-claude-code` и другие) — они реальны, но
вокруг них много непроверенных цифр. Например, у одного репозитория заявлено
94 тысячи звёзд за четыре месяца — это ненормальный темп роста для GitHub, и
источник сам это отмечает <cite index="60-1">a GitHub repository called Caveman hit 94,000 stars in under four months, one of the fastest climbs in recent memory — the repo's self-published benchmarks claim token reductions between 22% and 87%, though those numbers aren't independently verified</cite>.
Честная версия того же репозитория прямо признаётся: экономятся только
**выходные** токены, входные — нет, а сам скилл добавляет 1–1.5 тысячи
токенов в каждый запрос <cite index="64-1">Caveman only shrinks output tokens — input and reasoning tokens are untouched, and the skill itself adds roughly 1,000 to 1,500 input tokens per turn, so whole-session savings run smaller than the output number and can even go net-negative on already-terse workloads</cite>.

Я сознательно не подключаю это в проект. У вас в настройках стоит требование
показывать пошаговое рассуждение и проверяемость — телеграфный стиль этому
прямо противоречит. Если сами захотите попробовать на бытовых задачах вне
этого проекта — репозиторий существует, но не для site-factory.

## Что не проверено в этом файле

1. Конкретные проценты экономии токенов у caveman-скиллов (22–87%,
   65%, 40%) — самозаявленные бенчмарки авторов, независимой проверки нет.
2. Число звёзд у `claude-hud` (в одном источнике — 23 тысячи, в другом —
   27.3 тысячи на близких датах) — расхождение между источниками, не
   выяснял, какое актуальнее.
3. Точные тарифы Sonnet/Opus/Haiku на сегодня — не проверял на
   claude.com/pricing, эта страница не была мне доступна для прямой
   проверки в рамках диалога. Смотрите официальную страницу перед
   планированием бюджета.
4. Утверждение про статус фичи per-agent provider routing взято из открытого
   issue на GitHub (`#38698`) — это подтверждает, что запрос существует и не
   закрыт на дату проверки, но не гарантирует, что фича не появится позже.
