# Site Factory — правила проекта

Это студия по производству сайтов. Каждый заказ живёт в `sites/<slug>/`.
Бриф каждого заказа — в `brief/<slug>.md`.

---

## Стек по умолчанию

- **Vite + React 19 + TypeScript**
- **Tailwind CSS v4**
- **GSAP** для скролл-анимаций, **Motion (framer-motion)** для микро-переходов
- Деплой: статика (`npm run build` → `dist/`)

Отклоняйся от стека, только если бриф прямо требует другого (WordPress, Tilda,
Next.js с SSR под большой каталог). Тогда скажи об этом вслух до начала работы.

---

## Жёсткие правила (нарушение = переделка)

### Типографика
- Шрифты **Inter, Roboto, Open Sans, Montserrat, Poppins — запрещены** как основные.
  Это шрифты по умолчанию, они читаются как «сделано нейросетью».
- Максимум 2 семейства: одно дисплейное, одно текстовое.
- Размеры — по типографской шкале, не произвольные пиксели.

### Цвет
- Никаких сиренево-синих градиентов. Никаких `#6366f1`, `#8b5cf6`, `#a855f7`.
- Все цвета — CSS-переменными в `:root`. Ни одного захардкоженного hex в компонентах.
- Контраст текста — минимум WCAG AA (4.5:1 для основного текста).

### Вёрстка
- Сетка 4px или 8px. Отступы кратны шагу сетки.
- Карточка внутри карточки — запрещено.
- Не делать «четыре карточки в ряд» как решение по умолчанию. Если ряд карточек —
  единственная идея раздела, раздел спроектирован плохо.
- Обязательные брейкпоинты для проверки: **390px** и **1920px**.

### Движение
- Анимировать только `transform` и `opacity`. Не `width`, `height`, `top`, `left`.
- Выход быстрее входа (типично 150ms out / 250ms in).
- `@media (prefers-reduced-motion: reduce)` — обязательно в каждом проекте.
- Не начинать появление со `scale(0)`.

### Контент
- **Никаких `lorem ipsum` и выдуманных фактов.** Если данных в брифе нет — ставь
  `[[НУЖНО ОТ КЛИЕНТА: описание]]` и вынеси список таких мест в конце работы.
- Не выдумывай сертификаты, цифры, года основания, количество клиентов, отзывы,
  логотипы партнёров — вне зависимости от ниши. Выдуманный факт в любой сфере стоит клиенту репутации.

### Тон
Тон определяется нишей и аудиторией из брифа — не задан заранее. Кто читает сайт и
в каком состоянии принимает решение — это первый вопрос перед любым текстом.
- У инженера-снабженца в голове допуски и сроки поставки.
- У родителя, выбирающего секцию ребёнку, — безопасность, тренер, расписание.
- У клиента косметолога — результаты, отзывы, доверие к специалисту.
Тон, длина предложений, степень формальности — всё выводится из этого, не из привычки.

## Порядок работы

Никогда не начинай верстать сразу. Порядок:

1. **Бриф** → `brief/<slug>.md`. Нет брифа — сначала собери его.
2. **Направление** → 3 разных концепции словами (не кодом). Ждать выбора человека.
3. **Токены** → `sites/<slug>/src/styles/tokens.css`. Показать палитру и шрифты.
4. **Контент** → тексты всех секций до вёрстки.
5. **Изображения** → собрать промпты по схеме и сгенерировать до вёрстки.
6. **Вёрстка** → секция за секцией, не всё сразу.
7. **Движение** → только после того, как статика согласована.
8. **Визуальный QA** → Playwright, скриншоты 390 и 1920, список дефектов, правки.

Переход к следующему шагу — только после явного «ок» от человека на шагах 2 и 3.

## Изображения

**Инструмент генерации доступен — значит, им пользуются.** Сайт из одной галереи
и десяти секций текста на однотонном фоне читается как «сделано нейросетью»
не меньше, чем шрифт Inter. Шаг 5 в порядке работы пропускать нельзя.

Схема промпта, граница честности и порядок вызова —
`docs/06-ГЕНЕРАЦИЯ-ИЗОБРАЖЕНИЙ.md`.

Коротко про границу: **фактуры и атмосферу генерируем, документальное — нет.**
Работы мастеров, интерьер, портреты сотрудников, отзывы с именами берём у клиента.
Человек приедет по адресу и сверит увиденное с реальностью.

Сгенерированное обязательно пережимать: `scripts/optimize-image.mjs`.
Модель отдаёт PNG на 1–2 МБ, в таком виде на страницу их не ставят.

## Скиллы

Установлен 21 скилл. Большая часть — конкурирующие слои вкуса: они говорят об
одном и том же разными словами и противоречат друг другу в деталях.

**Слой вкуса — строго один за раз.** Это не рекомендация: два одновременно дают
взаимоисключающие указания, и работа останавливается на согласовании инструкций,
а не на задаче.

| Задача | Скилл |
|---|---|
| Лендинг, портфолио, редизайн — основной выбор | `design-taste-frontend` |
| Механическая проверка вёрстки на AI-признаки | `impeccable` |
| Продуктовый UI, дашборды, настройки | `interface-design` |
| Спокойный «дорогой» интерфейс | `soft-skill` |
| Редакционный минимализм в духе Linear | `minimalist-skill` |
| Аудит и подтяжка готового сайта | `redesign-skill` |
| Вытащить стиль с референса | `design-dna` |
| Запретить обрезанную выдачу | `output-skill` |

Генерация изображений — `imagegen-frontend-web`, `imagegen-frontend-mobile`,
`brandkit`, `image-to-code-skill`. Они не спорят со слоями вкуса, включать можно
вместе с любым.

`ui-ux-pro-max`, `frontend-design`, `ui-styling`, `design-system`, `brand`,
`theme-factory` — дублируют перечисленное. Держим установленными, но по умолчанию
не трогаем: каждый вызов грузит десятки тысяч токенов ради того же совета.

## Дисциплина токенов

- `/clear` между разными заказами — не тащи контекст клиента А в работу над клиентом Б.
- `/compact` внутри одного заказа при заполнении контекста ~60%, не жди 90%.
- Не подключай MCP «про запас» — Figma MCP добавляй только когда пришёл заказ с готовым макетом.
- Подробный разбор и почему Obsidian/Ollama здесь не нужны — `docs/05-ЭКОНОМИЯ-ТОКЕНОВ.md`.

## Чего не делать никогда

- Не коммитить в git без явной просьбы.
- Не деплоить без явной просьбы.
- Не ставить npm-пакеты «на всякий случай». Каждая зависимость — обоснована.
- Не писать «готово», если не прогнал визуальный QA.
- Не копировать дизайн конкурента пиксель в пиксель. Извлекать принципы — можно,
  копировать — нет.
- Не брать чужие логотипы, фотографии и шрифты без лицензии. Только собственные
  ассеты клиента, либо шрифты с открытой лицензией (Google Fonts, Fontshare),
  либо изображения с явной лицензией.
