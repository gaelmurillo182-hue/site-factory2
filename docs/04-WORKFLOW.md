# 04 · Как это работает целиком

## Схема одного заказа

```
   ваш текст о компании
            │
            ▼
   /brief  ──────────────►  brief-analyst  ──►  brief/<slug>.md
            │                                    + список [[НУЖНО ОТ КЛИЕНТА]]
            ▼
   /new-site brief/<slug>.md
            │
            ├─ 1. art-director  ──►  3 направления словами
            │                        ⏸ СТОП — вы выбираете
            │
            ├─ 2. art-director  ──►  tokens.css (цвета, шрифты, сетка)
            │     copywriter    ──►  content.md (все тексты)
            │                        ⏸ СТОП — вы подтверждаете
            │
            ├─ 3. frontend-builder ──►  секция → показ → секция → показ
            │
            ├─ 4. motion-engineer  ──►  GSAP, переходы, reduced-motion
            │
            └─ 5. visual-qa        ──►  Playwright, 390px + 1920px
                                        список дефектов → правки → повтор
                                             │
                                             ▼
                                    sites/<slug>/dist/
```

## Почему две остановки

Модель по умолчанию доводит задачу до конца за один заход. На сайтах это плохо:
если направление выбрано неверно, все восемь часов работы уходят в мусор.

Две контрольные точки — направление и токены — стоят пять минут вашего внимания
и спасают весь остальной цикл. Не пропускайте их, даже когда хочется быстрее.

## Почему агенты, а не один длинный чат

У каждого субагента свой контекст. Когда `visual-qa` читает 40 скриншотов и
разбирает CSS, это не забивает основной диалог — обратно приходит только список
дефектов. Основной контекст остаётся чистым, и качество к концу проекта не падает.

Обратная сторона: субагенты тратят больше токенов, потому что каждый держит
свой контекст. Для мелких правок агенты не нужны — правьте напрямую.

## Роли: скилл, агент, MCP

| Что | Это | Пример |
|---|---|---|
| **Скилл** | правила, которые загружаются в текущий контекст | `frontend-design` учит, каким должен быть дизайн |
| **Субагент** | отдельный работник со своим контекстом | `visual-qa` уходит смотреть сайт и возвращается с отчётом |
| **MCP** | канал к внешнему инструменту | `playwright` даёт доступ к настоящему браузеру |
| **Команда** | заготовленный промпт под слэшем | `/new-site` запускает весь пайплайн |

Скилл говорит **как** делать. Агент — **кто** делает. MCP — **чем**. Команда — **когда**.

## Куда что складывается

```
site-factory/
├── brief/
│   ├── lavitek.md
│   └── zavod-x.md
└── sites/
    ├── lavitek/
    │   ├── content.md
    │   ├── src/styles/tokens.css
    │   ├── src/sections/
    │   └── dist/            ← готовая статика на заливку
    └── zavod-x/
```

Один заказ — одна папка в `sites/`. Бриф — в `brief/`. Ничего не смешивается.

## Сколько это занимает

Ориентировочно, для одностраничника промышленной компании:

| Этап | Ваше время | Время агента |
|---|---|---|
| Бриф | 20–40 мин (ответы на вопросы) | 5 мин |
| Направления + выбор | 10 мин | 10 мин |
| Токены + тексты | 15 мин (вычитка) | 15 мин |
| Вёрстка | 30 мин (приёмка секций) | 40–90 мин |
| Движение | 10 мин | 20 мин |
| QA и правки | 20 мин | 30 мин |

Основное время уходит не на генерацию, а на ваши решения. Это и есть та часть,
которую нельзя делегировать: какое направление выбрать, что считать хорошим.

## Типичные ошибки первых недель

**Ставить все 42 скилла.** Они конфликтуют и забивают контекст. Четыре слоя:
вкус, токены, движение, глаза.

**Пропускать остановки.** «Пусть сразу сделает всё» → переделка с нуля.

**Не ставить Playwright.** Модель без глаз уверенно рапортует о готовности
сайта с горизонтальным скроллом на мобильном.

**Принимать выдуманные факты.** Модель заполнит пробел правдоподобной цифрой,
если ей не запретить. В B2B это дороже, чем плохой дизайн.

**Просить «сделай красиво».** Это просьба выдать среднее. Запрещайте конкретное.

**Смешивать слои вкуса.** `frontend-design` + `impeccable` + `taste-skill`
одновременно = компромисс между тремя мнениями = снова середина.
